# Pi through Magpie

Magpie manages upstream providers and keys. Meerkat schedules tasks and retains
their frozen execution profiles. Pi connects to Magpie's local API:

```text
Meerkat → Pi → http://127.0.0.1:3425/v1 → Magpie key routing → provider
```

This configuration was checked against Magpie **0.1.568** and Pi **0.99.1**.
It does not require a new Meerkat executor. Paid generation and multi-account
failover have not been verified in this integration.

## Configure Magpie

In Magpie's Providers view, add one provider with its upstream endpoint, then
add the other keys to that provider. Use separate names such as `Key 01` and
`Key 02`. Enable the keys you want routed. Enter real keys in Magpie; do not put
them in shell command arguments, repository files or chat messages.

For several independent accounts, use `routing=rotate` with `stays=session`:
new conversations rotate between keys, while an active conversation stays
with the key that answered it. An unavailable key can be skipped. For a
preferred account followed by backups, use `routing=order` instead. Avoid
switching keys on every request when prompt-cache reuse matters. These
settings are available on the provider's routing controls in this version;
its provider CLI does not expose them as `set` flags.

Use the provider/model identifier Magpie exposes, including every namespace.
For example, an upstream `vendor/model` under provider `relay` is
`relay/vendor/model` at Magpie, and `magpie/relay/vendor/model` in Pi's picker.
Pick that model from Magpie's Pi agent row or run:

```sh
magpie pi magpie/relay/vendor/model
```

Keep Magpie running while Pi uses it. This version's default gateway is bound
to loopback and accepts a placeholder bearer token; `magpie` is a client
identifier, not an upstream secret. Do not expose this gateway on a LAN.
Later Magpie versions can have a different authentication contract; use the
client token generated by the installed version when required.

## Configure Meerkat

Use a new private profile for future tasks; existing frozen tasks retain their
original profiles. The model below must exist in your Magpie catalog.

```sh
export MAGPIE_API_KEY=magpie
node scripts/configure.mjs --project-id example --provider magpie \
  --model relay/vendor/model --auth-env MAGPIE_API_KEY \
  --base-url http://127.0.0.1:3425/v1 --api openai-completions \
  --pi-command /abs/path/to/pi
node scripts/launch.mjs doctor --profile /Users/me/.meerkat/profiles/example.json \
  --probe-executor
```

The profile and isolated Pi model file store `${MAGPIE_API_KEY}`, never upstream
keys. Start Meerkat's service from the shell with that variable exported.
Different roles can use separate profiles and model identifiers, while sharing
the same Magpie provider key pool. Retain the exact configured model in the
frozen task; do not change routing to another model during its run.

The request-budget bridge currently supports text `openai-completions` only.
Use that API even when the upstream also offers Anthropic or Responses.
Static configuration and executable-version checks do not prove tool calling,
raw SSE usage reporting, paid account readiness or actual task delivery.

## Usage and retries

Meerkat authorizes Pi-to-gateway requests. Magpie may attempt more than one
upstream key before a request succeeds. One Meerkat request therefore does
not imply one upstream attempt. A failed or lost upstream attempt can incur
cost that the final response does not describe. Compare Magpie's routing/usage
records with the provider's billing records before treating totals as complete.

Meerkat retains unknown fees and usage as unknown. Its input reservation is an
estimate, not a monetary cap. A provider's balance is not inferred from the
number of keys, and several keys in one account need not have independent
allowances. A gateway route does not bypass an exhausted provider account.
